# Оценка по критериям финала

`scripts/evaluate.py` и `python -m gabarit evaluate` сохраняют прежние поля
сводки и JSONL, добавляя дальности двух стадий детекции, наблюдаемость габарита,
его временную устойчивость, фильтрацию и выполнение бюджета 100 мс.

```sh
python -m gabarit evaluate data/extracted/for_hackathon --out artifacts/eval_finalist
python -m gabarit evaluate data/extracted/falcon_test --config config/falcon_prime_ros.yaml --out artifacts/eval_falcon
python -m gabarit evaluate data/extracted/for_hackathon --annotations annotations.json --fn-cost 5 --out artifacts/eval_labelled
```

Для корректного сравнения конфигураций используйте одни и те же записи,
оборудование, оси, диапазон кадров и `--step 1`. `--start N` начинает новую
временную последовательность с исходного кадра N, без истории до него.
Параметр `--stop N` задаёт
исключительную верхнюю границу исходного номера кадра: обрабатываются индексы
`start, start+step, ... < N`. `--stop 0` сохраняет корректный пустой отчёт.
`--step` должен быть положительным, `--start`, `--stop` и `--progress` неотрицательными.
Пропуск кадров меняет работу временного подтверждения и движения; результаты
с разным `--step` непосредственно несопоставимы.

Для ручной проверки профиля добавьте `--save-path`: в JSONL появится `track`
с осью и высотой пути по дальности. `path_guard` сохраняется независимо от этого
флага; он показывает временную проверку рельсов под устойчивым рассеянным шумом.

## Новые bag с маркерами организаторов

Архив `new_synth_data_with_markers.zst` содержит три SQLite bag с темами
`/lidar_points` и `/synthetic_obstacle_markers`. Для детекции используется
только PointCloud2. Для отдельного экспорта MarkerArray штатным ROS-декодером:

```sh
docker compose exec gabarit gabarit shell
python3 scripts/export_bag_markers.py /data/extracted/finalist_markers_20261019 --out /output/organizer_markers
exit
```

Экспорт сохраняет timestamp записи, frame, namespace, ID, действие, тип,
позицию, quaternion, scale, цвет, текст и локальные точки маркера. `DELETE`
не означает присутствующий объект; линии `LINE_LIST` нужно сначала повернуть
quaternion и перенести pose. `scale.x` у такого маркера — толщина линии,
а не размер препятствия. Запись содержит также части человека и частицы пыли:
число маркеров не равно числу физических препятствий.

Сопоставляйте облако и маркеры по timestamp bag, проверяя frame_id. В новых
записях header stamp отличается от времени записи; смешивать эти две шкалы
нельзя. Видимость, положение относительно габарита и число возвратов требуют
отдельной проверки. Пересечение боксов с допуском — диагностическое соответствие,
а не строгая оценка FP/FN на всех физических объектах. Итоги и конкретные
неподтверждённые объекты приведены в [отчёте 19.10](DETECTION_VALIDATION_2026_10_19.md).

## Соответствие критериям

| Критерий экспертов | Поля отчёта и способ проверки |
| --- | --- |
| 1. Дальность первого детекта | `candidate_events[].first_candidate_distance_m` и `events[].first_confirmed_distance_m`, кадры и задержка подтверждения |
| 2. Дальность габарита | `envelope.current_observed_until_m` отдельно от `envelope.envelope_until_m` и дальности удержанного габарита |
| 3. Устойчивость габарита | Доли удержания/потери, переходы доступности, `motion_compensated_stability` |
| 4. Ложноположительные срабатывания | `supervised_metrics.fp`, precision и specificity только с внешней разметкой |
| 5. Ложноотрицательные срабатывания | `supervised_metrics.fn`, recall, balanced accuracy и взвешенная цена ошибок только с разметкой |
| 6. Работа 10 Гц | p50/p95/p99, доля кадров в 100 мс отдельно для pipeline и чтения/декодирования/обработки |
| 7. Работа фильтра | Число проверенных/удалённых точек, доля удаления, время `timing_ms.filter`; сохранность препятствий проверяется разметкой |
| 8. Дополнительные функции | Наличие и сценарные проверки функций; эта сводка не назначает им экспертный балл |
| 9. Удобство запуска | Отдельная проверка Docker/RViz и управления bag из консоли; время вычислений её не подменяет |

## Дальность кандидата и подтверждённого препятствия

`candidate_events` объединяет наблюдения `pending` и `obstacles` по
идентификатору трекера. Включены кандидаты, ни разу не подтверждённые.
После `state_reset` начинается новая `sequence`: повторно выданный track_id
не объединяется с предыдущим событием. Число сбросов - `temporal_resets`.
`events` по-прежнему содержит только треки с подтверждённым препятствием;
прежние `first_frame`, `frames`, `first_distance_m`, `min_distance_m`, `box`
и остальные поля сохраняют смысл.

Добавлены:

- `first_candidate_frame` / `first_candidate_distance_m`: первая принятая
  кандидатом дальность, записанная оценщиком;
- `first_confirmed_frame` / `first_confirmed_distance_m`: первое подтверждение;
- `first_candidate_track_distance_m` / `first_confirmed_track_distance_m`:
  продольная координата ближней границы бокса;
- `confirmation_delay_frames`: разность исходных индексов кадров;
- `confirmation_delay_processed_frames`: число обработанных переходов между
  первым кандидатом и подтверждением, включая пропуски его наблюдений;
- `confirmation_delay_s`: разность временных меток bag.

Поля с `distance_m` без `track` означают евклидову дальность. Это наблюдаемые
события алгоритма, а не сопоставление физическим объектам из ground truth.
Ранний дальний кандидат сам по себе не доказывает корректное обнаружение.
Разбиение одного объекта на несколько треков тоже не считается автоматически
несколькими настоящими препятствиями. Число тревог `alarm_frames` не называется
числом ложных тревог.

## Габарит и временная устойчивость

`current_observed_until_m` показывает свежие измерения текущего кадра,
`envelope_until_m` включает ограниченное удержание предшествующего габарита.
Удержанный прогноз не считается свежим наблюдением. Доли `held_share`,
`degraded_share`, `no_envelope_share` могут пересекаться. Отсутствие габарита
определено как горизонт не дальше `track.start`. Переходы доступности считают
смену этого состояния между обработанными кадрами, `envelope_loss_transitions`
считает переходы от наличия габарита к его отсутствию.

Для соседних обработанных кадров предыдущая ось пути переносится в текущий
кадр функцией `propagate_track` с оценённым `displacement_m` от EgoMotion.
Сравнение идёт по общему горизонту двух габаритов, без экстраполяции за него.
Считаются RMS бокового и вертикального изменения и p95 абсолютного бокового
изменения; сначала по точкам пути в паре кадров, затем статистики этих значений
по парам. Пары, включающие удержанный прогноз, выделены в `held_pairs`;
`fresh_pairs` их исключает. Для первого кадра и отсутствующего общего габарита
оценки нет, в JSON записывается `null`.
На кадре со сбросом временного состояния предыдущий габарит тоже не сравнивается.

Это измерение дрожания оценки, а не точности относительно истинных рельсов.
Постоянно неверная ось может быть очень устойчивой. Ошибка EgoMotion тоже
влияет на результат. Для контроля ухода с путей нужна внешняя разметка геометрии
или проверка визуализации; двоичная разметка ниже такую точность не измеряет.

## Время и фильтр

Каждый компонент `timing_ms` содержит mean, p50, p95, p99, max и число измерений.
В дополнение к внутренним стадиям конвейера оценщик измеряет:

- `read_decode`: `BagReader.read`, включая SQLite и CDR PointCloud2;
- `process_call`: полный вызов `Pipeline.process_raw`;
- `end_to_end`: их сумму по реально прошедшему времени.

Внутреннее `timing_ms.decode` означает преобразование облака в рабочие массивы,
а не чтение CDR. `realtime.pipeline` относится к внутреннему `timing_ms.total`,
`realtime.end_to_end` включает чтение и CDR. Для каждого приведены доля выполнения
бюджета 100 мс, число превышений и вычислительная пропускная способность
`1000 / mean_ms`. Средний FPS выше 10 не гарантирует отсутствие отдельных
превышений; нужно смотреть p95/p99 и долю превышений.

Измерение `end_to_end` не включает отрисовку RViz, ROS-доставку, запись JSONL,
расчёт метрик, открытие bag и первоначальную загрузку программы. `fps_wall`
включает накладные расходы цикла оценщика, но тоже не отрисовку и не задержку
доставки датчика. Обработка идёт без искусственного ожидания частоты bag;
это локальная оценка производительности, не аттестация жёсткого реального
времени. Первый обработанный кадр включён, отдельного прогрева нет.
В сводку сохраняются конфигурация, версия Python/NumPy и сведения об ОС/CPU.

`filter.removed_points` суммирует число удалённых фильтром точек,
`examined_points` - число проверенных, `removed_share` - их отношение.
Отсутствующее измерение не записывается как нулевая нагрузка.
Удалённые точки без разметки не считаются доказанными пылью или шумом.

## Разметка и FP/FN

Файл `--annotations` имеет строгую схему:

```json
{
  "schema_version": 1,
  "bags": {
    "doubleT_obstacle": {
      "frames": [
        {"frame": 0, "obstacle": false},
        {"frame": 10, "obstacle": true},
        {"frame": 11, "obstacle": null}
      ]
    }
  }
}
```

Ключ bag должен точно совпадать с `bags[].bag` в `summary.json`. Это относительный
идентификатор каталога от переданного корня данных, не отображаемый заголовок.
`frame` - целый неотрицательный индекс сообщения выбранной темы PointCloud2,
начиная с нуля, в порядке timestamp/id. `obstacle: true` означает, что по принятой
схеме разметки в этом кадре есть хотя бы одно требующее тревоги препятствие
в оцениваемом габарите и диапазоне; `false` означает размеченное отсутствие.
Критерий видимости/требуемой реакции нужно определить до прогона одинаково для
всех конфигураций. `null` означает неизвестно. Отсутствующая запись кадра тоже
означает неизвестно и не считается отрицательным примером.

Дубликаты индексов, строки вместо boolean, отрицательные индексы и неоднозначная
версия схемы отклоняются. Считается пересечение реально обработанных кадров
и известных меток:

- TP: размечено препятствие, алгоритм выдал `obstacle=true`;
- TN: размечено отсутствие, алгоритм выдал `obstacle=false`;
- FP: размечено отсутствие, алгоритм выдал тревогу;
- FN: размечено препятствие, алгоритм не выдал подтверждённую тревогу.

`pending` не считается подтверждённой тревогой. Precision = TP/(TP+FP),
recall = TP/(TP+FN), specificity = TN/(TN+FP), balanced accuracy - среднее
recall и specificity, когда обе определены. При нулевом знаменателе результат
`null`, а не 0 или 1. Цена ошибок `FP + fn_cost * FN`; `--fn-cost 5` задаёт
относительную стоимость одного FN равной пяти FP. Это выбранная стоимость,
а не физическая вероятность аварии.

`excluded_unknown_frames` показывает число обработанных кадров без известной
метки, `annotation_frames_not_processed` - число размеченных индексов,
которые не попали в прогон из-за `--step`, `--stop` или диапазона записи.
Они не становятся FN. Несовпавшие bag ID и выбранные записи без разметки
перечислены в `report.annotations`. Без разметки `supervised_metrics.available`
равен false; FP/FN и производные показатели вообще не вычисляются.

Эта схема оценивает двоичное решение на кадр. Она не измеряет AP, IoU боксов,
полноту отдельных классов, объектную recall или долю пропущенных физических
препятствий, когда несколько объектов находятся в одном кадре.
