## 2. Краткое описание задачи хакатона

### 2.1. Проблема

Необходимо разработать систему, которая по последовательности облаков точек от установленного на поезде 3D-лидара определяет, свободен ли габарит движения беспилотного поезда в тоннеле метро.

Система должна своевременно обнаруживать посторонний объект внутри опасного габарита, определять расстояние до ближайшего препятствия и выдавать результат, пригодный для дальнейшего реагирования системы управления поездом или оператора.

Главная сложность задачи состоит не только в обнаружении объекта, но и в отделении реального препятствия от штатных элементов инфраструктуры:

- рельсов;
- шпал;
- стен и свода тоннеля;
- платформ;
- гермозатворов;
- кабельных конструкций;
- стрелок и соседних путей;
- людей и предметов, находящихся вне габарита движения.

### 2.2. Входные данные

Основной вход:

- последовательность сообщений `sensor_msgs/msg/PointCloud2`;
- сообщения сохранены в ROS 2 bag с хранилищем SQLite3;
- частота записей приблизительно 10 Гц;
- облако содержит координаты `x`, `y`, `z`, интенсивность, номер кольца и временную метку точки;
- одометрия и скорость движения не гарантируются;
- наличие интернета во время проверки не гарантируется.

Текущая реализация читает bag напрямую через SQLite3 и собственный CDR-декодер, поэтому для запуска веб-приложения ROS не требуется.

### 2.3. Обязательный результат обработки

Минимальный результат для каждого кадра или временного события:

- состояние пути: `свободно` или `препятствие`;
- расстояние до ближайшего препятствия;
- устойчивое событие, не исчезающее из-за единичного шумного кадра.

Дополнительные полезные поля:

- `track_id` объекта;
- координаты и габаритный бокс;
- ближайшая поверхность объекта;
- размеры видимой части;
- количество точек;
- уровень уверенности;
- диагностические причины решения;
- первый, подтверждённый и последний кадр события;
- история расстояния до объекта.

### 2.4. Опасная область

Подтверждённые ориентиры:

- высота габарита — около 3 м;
- ширина устно указывалась как 2,1–2,2 м;
- базовый минимальный объект — 300 × 300 × 100 мм;
- препятствием считается объект внутри габарита поезда, а не только непосредственно на рельсах;
- человек на платформе вне габарита не является препятствием;
- кабель или иной объект, попавший внутрь габарита, является препятствием.

Ширина, высота и запас безопасности должны оставаться параметрами конфигурации, а не быть безусловно зашитыми в интерфейс или алгоритм.

### 2.5. Требования к качеству

Основные критерии оценки:

1. отсутствие пропусков реальных препятствий;
2. минимальное количество ложных тревог;
3. дальность устойчивого обнаружения;
4. скорость обработки;
5. устойчивость на новых тоннелях и новых проездах;
6. воспроизводимость запуска;
7. понятность архитектуры и исходного кода;
8. наглядность демонстрации.

Ориентиры дальности из задания:

- менее 100 м оценивается слабо;
- 100 м — хороший базовый уровень;
- 200 м — очень хороший результат;
- 300 м — отличный результат при достаточной плотности данных и приемлемом числе ложных тревог.

Эти значения являются ориентирами оценки, а не подтверждёнными проходными порогами.

### 2.6. Ограничения среды

Решение должно:

- работать автономно после установки зависимостей;
- не зависеть от внешних API;
- не требовать соединения с интернетом во время обработки;
- использовать одну конфигурацию для всех bag;
- не содержать правил, привязанных к имени конкретного bag, номеру кадра или заранее известному расстоянию до объекта;
- корректно обрабатывать скрытые контрольные проезды.

## 3. Фактический датасет проекта

### 3.1. Сводка

В проекте локально проаудированы:

- 6 ROS 2 bag;
- 2 488 кадров;
- примерно 250,17 секунды записи;
- около 23,1 ГБ данных;
- частота около 10 Гц;
- 5 штатных проездов;
- 1 проезд с препятствиями.

### 3.2. Состав

| Bag | Кадры | Длительность | Назначение |
|---|---:|---:|---|
| `doubleT_obstacle` | 201 | 20,39 с | положительный проезд с человеком и отдельным кандидатом предмета |
| `doubleT_platform` | 345 | 34,42 с | штатный проезд около платформы |
| `roundT_doubleT` | 252 | 25,07 с | штатный переход между типами тоннеля |
| `roundT_pressureGate_roundT` | 268 | 26,70 с | штатный проезд через гермозатвор |
| `roundT_squareT_pressureGate_squareT` | 545 | 55,38 с | длинный штатный проезд с изменением геометрии |
| `squareT_platform_squareT_switch` | 877 | 88,21 с | штатный проезд с платформой и стрелкой |

### 3.3. Технические различия

- Пять bag содержат примерно 307 200 исходных точек на кадр.
- `doubleT_obstacle` содержит примерно 921 600 точек на кадр.
- Используются разные имена topic и разные значения frame.
- В облаках много нулевых заполнителей `(0, 0, 0)`, которые должны удаляться до анализа.
- Рабочее направление вперёд предварительно определено как `-Y`, поперечная координата — `X`, высота — `Z`.
- Устойчивое число возвратов на дальности более 100 м невелико, несмотря на единичные точки до 200 м.

### 3.4. Ограничения данных

- Нет официальной покадровой или объектной разметки.
- Есть только один положительный проезд.
- Положительный bag отличается от остальных плотностью и topic, поэтому модель не должна использовать эти признаки как сигнал наличия препятствия.
- Пять штатных сценариев недостаточны для доказательства обобщаемости.
- Нельзя смешивать результат на реальных данных и синтетических препятствиях в одну метрику.
- Нельзя объявлять предварительную локальную разметку официальным ground truth.

## 4. Текущая реализация проекта

### 4.1. Общая архитектура

```text
ROS 2 bag / SQLite3
        ↓
BagStore + CDR decoder
        ↓
нормализация и фильтрация точек
        ↓
геометрический detector ───── normal_scene.npz
        ↓
tracker и устойчивые события
        ↓
HTTP API + бинарное облако Float32
        ↓
веб-интерфейс + Three.js + журнал оператора

Дополнительная ветка:
точки → BEV → ONNX-модель → диагностический слой
```

### 4.2. Серверная часть

Реализовано:

- поиск bag в каталоге данных;
- прямое чтение `.db3`;
- декодирование `PointCloud2` без ROS;
- выбор кадра по индексу;
- применение единой конфигурации детектора;
- загрузка модели нормальной сцены;
- геометрическое обнаружение кандидатов;
- присвоение `track_id`;
- подтверждение устойчивых событий;
- формирование BEV;
- запуск ONNX в режимах Auto, GPU, CPU и Geometry;
- бинарная передача визуализируемых точек;
- сохранение решений оператора в JSONL;
- экспорт решений в JSON и CSV;
- ограничение одновременной тяжёлой обработки;
- проверка health/capabilities.

Текущие API:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | состояние сервера и наличие моделей |
| GET | `/api/capabilities` | доступные режимы обработки |
| GET | `/api/bags` | список bag и метаданные |
| GET | `/api/frame` | обработка и выдача одного кадра |
| GET | `/api/feedback` | журнал решений оператора |
| POST | `/api/feedback` | сохранение решения оператора |
| GET | `/api/export?format=json` | экспорт журнала в JSON |
| GET | `/api/export?format=csv` | экспорт журнала в CSV |

### 4.3. Геометрический алгоритм

Текущий pipeline включает:

1. удаление невалидных и нулевых точек;
2. ограничение рабочей области по дальности и высоте;
3. локальную оценку пола;
4. оценку положения рельсов и профиля пути;
5. построение коридора габарита по дальности;
6. использование резервного фиксированного центра при недостаточном покрытии;
7. сравнение с моделью штатной сцены;
8. диапазонное разбиение пространства;
9. кластеризацию кандидатов;
10. фильтрацию протяжённой инфраструктуры;
11. расчёт bbox, расстояния, высоты и количества точек;
12. временное подтверждение через tracker.

### 4.4. ML-ветка

Реализована компактная BEV-сегментационная модель:

- сформирован BEV-датасет;
- проведено обучение в PyTorch/CUDA;
- модель экспортирована в ONNX;
- проверены GPU, CPU и fallback;
- результат может визуализироваться как тепловая карта.

Ограничение: единственный положительный проезд участвовал в обучении. Независимого положительного теста нет. Поэтому ML сейчас является только диагностическим слоем и не должен принимать окончательное решение о тревоге.

## 5. Критическая оценка текущего решения

### 5.1. Сильные стороны

1. Реальный, а не макетный pipeline обработки LiDAR.
2. Отсутствие зависимости от ROS при пользовательском запуске.
3. Автономность после установки локальных зависимостей.
4. Поддержка различающихся topic, frame и плотности облака.
5. Один и тот же детектор используется в API и evaluator.
6. Есть временное подтверждение и стабильные идентификаторы.
7. Есть воспроизводимый полный прогон всех данных.
8. Есть честно задокументированные ограничения.
9. Интерфейс уже позволяет исследовать реальные облака и объекты.
10. ML не выдается за доказанную основу решения и оставлен advisory-only.

### 5.2. Критические недостатки алгоритма

#### A. Ложные тревоги

36 ложных устойчивых интервалов на пяти штатных записях — главный дефект. С учётом новой формулировки постановщика этот показатель важнее добавления новых визуальных функций.

Основные вероятные источники:

- рельсы и протяжённая инфраструктура превращаются в компактные кластеры после обрезки;
- фон хранится в координатах сенсора и не учитывает движение;
- разные участки тоннеля смешиваются в одной модели;
- резервный коридор недостаточно следует повороту;
- объекты могут разделяться на границах диапазонных зон;
- tracker подтверждает повторяющуюся геометрическую ошибку как событие.

#### B. Отсутствие ego-motion

Без оценки движения нельзя корректно:

- совмещать фон соседних кадров;
- различать неподвижную инфраструктуру и локальный объект;
- строить устойчивую карту тоннеля;
- прогнозировать положение трека;
- корректно работать при скорости до 85 км/ч.

#### C. Хрупкая геометрия пути

Если покрытие рельсового профиля ниже порога, центры коридора сбрасываются к фиксированному значению. Это уничтожает локально полезную геометрию и создаёт риск на поворотах и стрелках.

#### D. Простой tracker

Жадное связывание центров с порогом около 1,8 м не учитывает:

- скорость относительного движения;
- форму bbox;
- направление движения;
- пропуски наблюдения;
- изменение плотности с расстоянием;
- ego-motion.

При 85 км/ч поезд проходит примерно 2,3 м между кадрами на 10 Гц, поэтому фиксированный порог может быть физически недостаточным.

#### E. Недоказанная дальность

Наличие точек на 200 м не доказывает обнаружение объекта минимального размера. Нужны отдельные метрики плотности, устойчивости к шуму и синтетические проверки по диапазонам дальности.

### 5.3. Недостатки текущего сайта

#### A. Перегруженная компоновка

При размере окна 1280 × 720:

- общая высота страницы около 2415 px;
- содержимое боковой панели около 1792 px;
- основная 3D-сцена занимает примерно 413 × 390 px.

Главный объект демонстрации — облако LiDAR — оказывается визуально меньше служебных панелей.

#### B. Нет продуктовой навигации

Сайт представляет собой одну длинную инженерную страницу. Посетитель не может быстро понять:

- какую проблему решает проект;
- как выглядит результат;
- как работает алгоритм;
- какие метрики достигнуты;
- какие ограничения честно признаются.

#### C. Настройки смешаны с демонстрацией

Выбор backend, слоёв, коридора и сравнения алгоритмов постоянно занимает экран. Эти элементы нужны разработчику, но не должны быть первыми объектами для посетителя.

#### D. Недостаточно понятное окружение 3D-сцены

Сейчас отсутствует ясный визуальный контекст:

- где поезд;
- где установлен LiDAR;
- куда направлено движение;
- где начинается контролируемая область;
- какие точки относятся к тоннелю;
- какой масштаб и расстояние до объекта.

#### E. Некоторые функции выглядят полнее, чем реализованы

- «Фоновая карта» фактически отображает пунктирную осевую линию.
- «Сравнение алгоритмов» в основном меняет поясняющий текст, а не два фактических результата.
- Таймлайн хранит только кадры, открытые в текущей сессии браузера.
- «История объекта» не содержит полноценной траектории.
- Обратная связь привязана к bag и кадру, но не к `track_id`.
- Метрика времени показывает `processing_ms` детектора, но не полную задержку API и рендера.
- FPS зависит от интервала между вызовами render и становится некорректным после паузы или ручной навигации.

#### F. Нет UI-регрессионных тестов

Не проверены автоматически:

- переходы навигации;
- переключение bag;
- воспроизведение;
- отмена устаревших запросов;
- выбор объекта в 3D;
- режимы камеры;
- панель настроек;
- таймлайн;
- фильтры журнала;
- ошибки сервера и пустые состояния;
- адаптивная компоновка.

## 7. Целевая концепция нового сайта

### 7.1. Главная идея

Новый сайт должен выглядеть не как панель настройки детектора, а как законченный продукт, который за первые 15–30 секунд отвечает на четыре вопроса:

1. Какую проблему решает система?
2. Что именно она обнаруживает?
3. Как выглядит результат на реальных данных?
4. Насколько решение быстрое и надёжное?

После этого заинтересованный эксперт должен иметь возможность перейти к техническим деталям, настройкам и ограничениям.

### 7.2. Целевые аудитории

#### Посетитель или член жюри

Нужно:

- быстро понять ценность решения;
- увидеть реальную работу;
- прочитать короткое объяснение;
- увидеть честные метрики;
- не разбираться в порогах и backend.

#### Технический эксперт

Нужно:

- изучить pipeline;
- выбрать bag и кадр;
- включить диагностические слои;
- посмотреть bbox, track, причины и тайминги;
- проверить ограничения и воспроизводимость.

#### Разработчик команды

Нужно:

- менять параметры;
- сравнивать режимы;
- локализовать ложные тревоги;
- экспортировать события;
- видеть полные диагностические данные.

### 7.3. Принцип двух уровней сложности

По умолчанию открывается посетительский режим. Он показывает только:

- текущий статус пути;
- ближайшее расстояние;
- число подтверждённых объектов;
- большую 3D-сцену;

Инженерные функции открываются через кнопку «Настройки и диагностика» в выезжающей панели:

## 9. Полная переработка 3D-сцены

### 9.1. Визуальный контекст

Новая сцена должна содержать:

- условную переднюю часть кабины или нос поезда;
- физически понятную точку установки LiDAR;
- маркер сенсора;
- конус или сектор наблюдения;
- направление движения;
- рельсы с заметной толщиной;
- шпалы с разумным шагом;
- полотно пути;
- стены и свод тоннеля;
- габарит поезда;
- отметки расстояния;
- объекты и их bbox;
- легенду цветов.

Окружение должно помогать ориентироваться, но не закрывать реальные точки LiDAR.

### 9.2. Координаты и масштаб

Единая визуальная система:

- `X` — поперёк пути;
- `Y` или отображаемая продольная ось — вперёд;
- `Z` — вверх;
- нулевая точка — позиция LiDAR;
- движение вперёд визуально направлено от нижней части экрана вглубь сцены;
- расстояние подписывается через 10 м до 100 м и через 25 м далее;
- возле LiDAR отображается отметка `0 м`.

Если внутренний формат использует `-Y` вперёд, преобразование должно выполняться централизованно в viewer, а не разными формулами в каждом слое.

### 9.3. Цветовая система

Рекомендуемая семантика:

- реальные точки: нейтральный бирюзовый или цвет по высоте;
- рельсы: светло-серый металл;
- безопасный габарит: прозрачный зелёно-бирюзовый;
- кандидат: янтарный;
- подтверждённое препятствие: красный;
- выбранный объект: белая или голубая обводка;
- штатная инфраструктура: приглушённый серо-синий;
- ML heatmap: отдельная шкала, видимая только при включении;
- ошибочные/отклонённые события: серый или фиолетовый.

Цвет не должен быть единственным носителем статуса: дополнительно используются форма, подпись и иконка.

### 9.4. Камеры

Оставить четыре осмысленных режима:

1. **Из кабины** — режим по умолчанию, LiDAR и путь впереди.
2. **Сверху** — оценка попадания объекта в габарит.
3. **Сбоку** — высота и продольное расстояние.
4. **К объекту** — фокус на выбранном `track_id`.

Требования:

- камера не сбрасывается при каждом новом кадре;
- смена bag сбрасывает её в режим по умолчанию;
- фокус недоступен без выбранного объекта;
- есть кнопка «Вернуть вид»;
- near/far plane и плотность точек не создают мерцания;
- камера не должна входить внутрь геометрии поезда или тоннеля.

### 9.5. Слои

Посетительские слои по умолчанию:

- облако;
- рельсы;
- габарит;
- объекты;
- окружение.

Диагностические слои:

- локальный пол;
- профиль центра пути;
- модель штатной сцены;
- rejected clusters;
- BEV heatmap;
- точки, использованные детектором;
- треки и прогноз положения.

Слой «Фоновая карта» разрешено оставить только после реализации фактической карты. До этого он должен называться «Осевая линия» или «Профиль пути».

### 9.6. Производительность 3D

- ограничивать визуализируемые точки независимо от числа обрабатываемых;
- использовать переиспользуемые `BufferGeometry` и typed arrays;
- не пересоздавать материалы каждый кадр;
- удалять GPU-ресурсы при смене bag;
- обновлять только изменившиеся слои;
- не строить невидимый heatmap;
- при падении FPS автоматически уменьшать число визуализируемых точек, не меняя вычисления детектора;
- отдельно показывать `processed points` и `rendered points`.

## 10. Панель настроек и инженерный режим

### 10.1. Общие требования

Панель открывается справа, не уводит пользователя со страницы и закрывается клавишей Escape.

Группы настроек:

1. отображение;
2. алгоритм;
3. обработка;
4. диагностика;
5. журнал и экспорт.

- переключатели слоёв;

- Auto;
- GPU;
- CPU;
- Geometry.

- inference time;

- network time;
- render time;

- FPS воспроизведения;

## 11. Переработка данных интерфейса и API

### 11.1. Проблема текущего подхода

Клиент получает и накапливает часть аналитики по мере просмотра. Из-за этого:

- таймлайн неполный;
- история объекта исчезает после перезагрузки;
- FPS и время обработки смешивают разные понятия;
- сравнение режимов не воспроизводимо;
- журнал не привязан к объекту.

### 11.2. Новые серверные представления

Рекомендуемые endpoint:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/project` | краткие сведения и версия сборки |
| GET | `/api/bags` | список записей |
| GET | `/api/bags/{bag_id}/summary` | длительность, кадры, precomputed events и метрики |
| GET | `/api/bags/{bag_id}/timeline` | полный таймлайн событий |
| GET | `/api/bags/{bag_id}/tracks/{track_id}` | история выбранного объекта |
| GET | `/api/frame` | один кадр и бинарные точки |
| GET | `/api/results` | зафиксированный evaluation summary |
| GET | `/api/config/public` | публичные параметры и их допустимые диапазоны |
| POST | `/api/feedback` | решение по конкретному `track_id` |
| GET | `/api/feedback` | фильтруемый журнал |
| GET | `/api/export` | экспорт журнала |

Существующие пути можно сохранить для совместимости, постепенно переводя клиент на новую схему.

### 11.3. Контракт feedback

Минимальные поля:

```json
{
  "bag": "doubleT_obstacle",
  "frame_index": 42,
  "track_id": 7,
  "event_id": "doubleT_obstacle:7:39",
  "decision": "confirmed",
  "nearest_distance_m": 56.4,
  "comment": "",
  "session_id": "...",
  "recorded_at": "..."
}
```

`track_id` обязателен, если в кадре есть несколько объектов. Решение по кадру без объекта допускается только для статуса «кадр проверен» и должно иметь другой тип записи.

### 11.4. Предварительный расчёт timeline

При первом запросе summary сервер:

1. проверяет наличие кэшированного результата с версией конфигурации;
2. при отсутствии запускает последовательный evaluator;
3. сохраняет только компактные метаданные событий;
4. сообщает клиенту прогресс;
5. не блокирует выдачу отдельных кадров;
6. инвалидирует кэш при изменении модели или конфигурации.

Для демонстрационной сборки summary лучше подготовить заранее.

### 11.5. Полные тайминги

Сервер должен возвращать раздельно:

```json
{
  "timing_ms": {
    "read": 0,
    "decode": 0,
    "geometry": 0,
    "bev": 0,
    "inference": 0,
    "tracking": 0,
    "serialization": 0,
    "server_total": 0
  }
}
```

Клиент добавляет:

- network time;
- binary decode time;
- render preparation;
- WebGL render time;
- end-to-end time.

Допустимо сохранить обычный JavaScript без сборщика, используя ES modules. Это уменьшает риск перед дедлайном и сохраняет автономность.

### 12.1. State model

Единое состояние должно содержать:

- route;
- server health;
- capabilities;
- список bag;
- выбранный bag;
- текущий кадр;
- состояние воспроизведения;
- полный timeline;
- список событий;
- выбранный `track_id`;
- настройки viewer;
- параметры detector;
- feedback текущей сессии;
- активный запрос и request id;
- измерения клиента.

Изменение state должно инициировать точечное обновление нужного компонента, а не полный ручной render всего экрана.

### 12.2. Маршрутизация

- History API с fallback на `index.html`;
- прямое открытие `/demo` должно работать;
- Back/Forward браузера должны переключать разделы;
- выбранный bag и кадр можно хранить в query string;
- технические настройки не должны попадать в URL, если не требуется воспроизводимая диагностическая ссылка.

## 16. Риски и меры снижения

| Риск | Последствие | Мера |
|---|---|---|
| Переработка UI ломает текущую demo-функцию | потеря рабочего прототипа | сначала baseline commit, затем поэтапная миграция |
| Новый 3D-контекст снижает FPS | плохая демонстрация | instancing, переиспользование геометрии, отключаемые environment layers |
| Timeline требует полного прогона | долгое открытие страницы | precomputed summary и versioned cache |
| Метрики расходятся с evaluator | недоверие к результатам | единый JSON-источник |
| Настройки меняют benchmark | несопоставимые цифры | показывать modified-config badge и config hash |
| ML выглядит как финальная модель | неверная интерпретация | явная маркировка advisory-only |
| Feedback неоднозначен | неверные пользовательские записи | обязательный `track_id` |
| Новый роутинг ломает прямые URL | сайт открывается только с главной | server-side SPA fallback и route tests |
| Поздний большой рефакторинг | нет времени на регресс | функциональная заморозка и запрет P2 до прохождения P0/P1 |
