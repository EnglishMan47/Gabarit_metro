# Гибридный ML-runtime: GPU, CPU и геометрический резерв

## Цель

Финальное приложение использует одну компактную BEV-модель в формате ONNX. При наличии работоспособного ускорителя модель исполняется на GPU; без него — на CPU. Если модель или ONNX Runtime недоступны, приложение продолжает работать с текущим геометрическим детектором. ROS и Docker в runtime не используются.

Геометрия не отключается при работе ML: она строит габарит, проверяет положение и размер сегментов, вычисляет расстояние и выполняет временное подтверждение. ONNX-модель добавляет карту вероятности препятствия внутри габарита.

Текущая экспериментальная модель уже обучена и интегрирована. Из-за отсутствия независимого положительного проезда её результат показывается как диагностика и не изменяет тревогу (`advisory_only`). Переход к объединённому решению разрешается после ручной проверки разметки и теста на новых положительных проездах.

## Режимы интерфейса

| Режим | Поведение |
|---|---|
| `Авто` | Проверить модель и доступные ONNX-провайдеры, выполнить короткий прогрев и выбрать GPU, если он работает и даёт выигрыш; иначе выбрать CPU; при ошибке перейти на геометрию |
| `GPU` | Попытаться использовать CUDA-провайдер; при недоступности явно показать причину и перейти на CPU, затем на геометрию |
| `CPU` | Выполнять ONNX через CPU; при ошибке перейти на геометрию |
| `Геометрия` | Не запускать ONNX и использовать существующий детектор |

Переключатель относится к сессии браузера и не изменяет конфигурацию других пользователей. Фактически выбранный backend всегда показывается рядом с FPS и задержкой.

## Порядок выбора в режиме `Авто`

1. Проверить наличие и контрольную сумму файла модели.
2. Проверить импорт ONNX Runtime и список execution providers.
3. Если доступен `CUDAExecutionProvider`, создать GPU-сессию и выполнить прогрев на входе нужной формы.
4. Сравнить медиану нескольких прогревочных запусков с CPU. GPU выбирается только при успешном результате и измеримом выигрыше.
5. Если CUDA недоступна или прогрев завершился ошибкой, создать `CPUExecutionProvider`.
6. Если ONNX-сессия не создаётся, вернуть результат геометрического детектора без остановки веб-приложения.

Наличие GPU не определяется только по имени видеокарты: решение принимается по реальному ONNX-провайдеру и успешному прогреву. Это учитывает несовместимые драйверы, нехватку памяти и неподдерживаемые операции модели.

## Контракт API

`GET /api/capabilities` возвращает:

```json
{
  "model_available": true,
  "onnxruntime_available": true,
  "providers": ["CUDAExecutionProvider", "CPUExecutionProvider"],
  "recommended_mode": "gpu",
  "fallback_available": true
}
```

Запрос кадра получает параметр `inference_mode=auto|gpu|cpu|geometry`. В ответ кадра добавляется:

```json
{
  "inference": {
    "requested_mode": "auto",
    "active_backend": "cuda",
    "model_used": true,
    "model_latency_ms": 12.4,
    "fallback_reason": null
  }
}
```

При резервном выполнении поле `fallback_reason` объясняет причину, например `model_missing`, `onnxruntime_missing`, `cuda_unavailable`, `session_failed` или `inference_failed`.

## Обучение и поставка

- Обучение выполняется в WSL на PyTorch с GPU, если CUDA доступна.
- Данные делятся целыми проездами, а не отдельными кадрами.
- Обученная модель экспортируется в ONNX и проверяется на совпадение выходов PyTorch/ONNX в допустимой численной погрешности.
- В поставку входит ONNX-файл, версия признаков, форма входа, контрольная сумма и метрики на отложенных проездах.
- Windows-runtime использует `onnxruntime-gpu` для NVIDIA либо `onnxruntime` для CPU. Эти пакеты не устанавливаются одновременно в одном окружении.
- Базовая установка без ML остаётся работоспособной и использует NumPy-геометрию.

## BEV-вход модели

Минимальный набор каналов для каждой ячейки:

1. нормализованное число точек;
2. максимальная высота над локальным полом;
3. средняя высота;
4. средняя интенсивность;
5. доля несовпадения с моделью штатной сцены в координатах лидара (регистрация движения пока отсутствует);
6. маска железнодорожного габарита;
7. временная устойчивость ячейки в соседних кадрах.

Выход — карта вероятности препятствия. Компоненты вне габарита игнорируются, а компоненты внутри передаются геометрической проверке и трекеру.

## Критерии готовности

- одинаковый ONNX-файл работает через CPU и GPU;
- ручной переключатель не требует перезапуска сервера;
- потеря GPU во время работы не останавливает обработку;
- резервный геометрический режим проходит существующие тесты и полный прогон;
- API и интерфейс показывают фактический backend и причину fallback;
- GPU и CPU сравниваются на одинаковых кадрах по качеству и задержке;
- независимый тест разделён по проездам и не использовался при настройке порога.

## Веб-визуализация

Three.js хранится локально в проекте вместе с MIT-лицензией, без CDN. Облако передаётся бинарным массивом `Float32Array`; метаданные кадра, боксы и события остаются в JSON. Отрисовка использует `BufferGeometry`. Декодирование ответа выполняется в основном потоке браузера; отдельный Web Worker пока не реализован.
